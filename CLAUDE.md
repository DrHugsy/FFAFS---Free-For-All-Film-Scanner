# Dr Iggy's — Free Design Tools

Este archivo es el contexto que Claude Code lee automáticamente al abrir esta carpeta. Léelo entero antes de tocar cualquier cosa — hay convenciones y trampas específicas de este proyecto que no son obvias a simple vista.

## Qué es esto

Un hub personal ("Dr Iggy's" — el nombre es por Iggy de JoJo's Bizarre Adventure, **no** por una iguana, aunque un asistente anterior asumió eso y hasta le dibujó una mascota de iguana; ver la sección de identidad visual) de herramientas gratis, sin registro, hecho por y para un usuario no-programador que viene guiando el desarrollo por chat con Claude durante muchas sesiones. El estilo de trabajo hasta ahora: pedidos conversacionales, iteración visual constante, y mucho cuidado en no romper lo que ya funciona.

**Nota sobre el nombre**: el sitio se llamó brevemente "Doctor Iggy's" (septiembre 2026) y después volvió a "Dr Iggy's" a pedido explícito del usuario ("no me gustó el Doctor"). Si ves "Doctor Iggy's" en algún commit viejo o en tu memoria de una sesión anterior, está obsoleto — el nombre correcto y actual es **"Dr Iggy's"**.

**Filosofía del proyecto — importante:**
- Todo tiene que seguir siendo **gratis** (ni para el usuario, ni idealmente para el dueño). No propongas soluciones pagas como primera opción.
- El usuario **no sabe programar**. No asumas que puede correr comandos de git/npm/etc. sin que se los expliques paso a paso, uno por vez, literal. Si le das varios comandos juntos, se pierde — pedilos de a uno.
- Cuando algo se puede verificar (renderizar, correr, probar), **verificalo antes de decir que funciona**. Este proyecto tiene un patrón establecido de usar Playwright (ya instalado en el entorno) para renderizar y probar cada cambio antes de entregarlo. No asumas que algo anda por leer el código — corré la app y mirá.

## Arquitectura

**Sin build step, sin framework, sin npm.** Cada página es un único archivo `.html` con `<style>` y `<script>` embebidos. Así se decidió a propósito, para que el usuario pueda editar/subir archivos sueltos sin entender de bundlers. **No introduzcas Vite/React/Webpack/etc. sin que el usuario lo pida explícitamente y entienda el cambio de flujo de trabajo que implica.**

## URLs limpias (sin `.html`) — importante para no romper

**Desde septiembre 2026 ninguna página del sitio se linkea con `.html` al final** (pedido explícito del usuario: "eso no es poco profesional?"). El mecanismo:

- `server_prod.py` tiene una ruta genérica `/<path:filename>` que primero busca el archivo tal cual, y si no existe y el pedido no termina en `.html`, prueba servir `filename + ".html"`. Así `/film-scanner` sirve `film-scanner.html` sin que haga falta una ruta a mano por cada página.
- Los nombres de archivo **son** el slug de la URL — por eso `cuarto-oscuro.html` se renombró a `film-scanner.html` y `favicon-gen.html` a `favicon-generator.html` (los demás ya tenían nombres en inglés que quedaban bien como URL: `photo-editor`, `lut-lab`, `convert`, `qr-generator`, `terms`). **Si agregás una herramienta nueva, el nombre del archivo debe ser directamente el slug que querés en la URL** — no hace falta tocar `server_prod.py`.
- Hay un diccionario `OLD_SLUG_REDIRECTS` en `server_prod.py` con redirects 301 de los dos nombres viejos (`cuarto-oscuro`, `cuarto-oscuro.html`, `favicon-gen`, `favicon-gen.html`) a las URLs nuevas, por si alguien tiene un link/marcador guardado. Si volvés a renombrar un archivo en el futuro, agregá su entrada acá también.
- **Todos los links internos usan rutas absolutas sin extensión** (`href="/film-scanner"`, `href="/"` para el hub), nunca `href="film-scanner.html"` ni `href="X.html"`. Esto aplica a: el `<a class="brand">`, el `.nav-menu`, los `<a class="tool-tile">` del hub, el footer, `<link rel="canonical">`, `<meta property="og:url">`, el JSON-LD (`index.html` y `film-scanner.html`), y cualquier `window.location.href = '...'` en JS (el handoff a Photo Editor en `film-scanner.html` y `lut-lab.html` usa `'/photo-editor'`). Si agregás una herramienta nueva o tocás cualquiera de estos, **no reintroduzcas `.html`**.
- `sitemap.xml` también usa las URLs limpias — actualizalo si agregás/renombrás una página.
- Para probar el ruteo sin desplegar: `preview_start` con `name: "flask-local"` (ver tabla de archivos) y navegar a `http://localhost:5050/lo-que-sea` con el Browser tool. `file://` no sirve para esto — el ruteo solo existe en el servidor Flask.

## Identidad visual — no la cambies sin permiso explícito

**El sitio pasó por tres identidades visuales.** Primero una estética "Windows XP retro" (ventanas con barra de título en degradado azul, tipografía Tahoma, fondo de lomas verdes), después un rediseño "premium" violeta/degradados, y en septiembre 2026 se asentó en el sistema actual tipo terminal. Si ves referencias a `--titlebar-1/2/3` azules, degradados violeta, un `<svg class="bg-scene">` de lomas y cielo, o texto tipo `$ whoami` en algún commit viejo o en tu memoria de una sesión anterior, **está obsoleto — no lo reintroduzcas.**

El sistema actual está inspirado en **cobalt.tools y en una terminal real de Windows** (referencia explícita del usuario — mandó una captura de `cmd.exe`, no calcada pero sí el espíritu): negro y blanco, tipografía monoespaciada, todo plano y con bordes finos, sin degradados ni sombras de color. Variables (`:root`) compartidas entre las 9 páginas (index, terms, about, film-scanner, photo-editor, lut-lab, convert, favicon-generator, qr-generator):
- `--bg:#000000` (negro puro), `--surface:#0E0E0E` / `--surface-2:#1A1A1A` / `--surface-3:#242424` (paneles, apenas más claros que el fondo)
- `--border:rgba(255,255,255,.14)`, `--border-strong:rgba(255,255,255,.32)` — bordes finos, nada de sombras
- `--text:#F2F2F2`, `--text-dim:#9A9A9A`, `--text-faint:#5C5C5C`
- Fuente: **Cascadia Mono** (Google Fonts, `<link>` directo — no hace falta build step). Antes era JetBrains Mono; el usuario pidió cambiarla ("proba otra") y esta es la fuente real que usa Windows Terminal/`cmd.exe`, que es justo la referencia que dio. Si el usuario vuelve a pedir cambiar la fuente, no vuelvas a JetBrains Mono sin que lo pida explícitamente.
- Estado activo/primario = **blanco sólido con texto negro** (no degradados de color) — así se ven los botones primarios, el toggle EN/ES activo, y el tag "Available"
- **Bordes cuadrados en todos lados** (border-radius:0) — pedido explícito del usuario, look "sharp tipo terminal".
- **Borde superior blanco más grueso (3px)** en las tarjetas de herramientas del hub (`.tool-tile`) y en los menús desplegables (`.nav-menu`) — es el detalle que le da el aire de ventana de terminal real (como una barra de título). Pedido explícito del usuario; no lo saques.
- Algunas variables viejas (`--violet-1/2/3`, `--titlebar-*`, `--ink`, `--window`, etc.) siguen existiendo como *alias* apuntando a la paleta nueva, para no tener que tocar cada selector del CSS. Si agregás una herramienta nueva, mejor usar los nombres nuevos directamente (`--bg`, `--surface`, `--text`, etc.) en vez de esos alias legacy.
- **Color de identidad por herramienta (septiembre 2026, pedido explícito del usuario)**: cada una de las 6 herramientas tiene un color fijo que la identifica, usado en dos lugares — (1) el fondo del ícono en su tarjeta del hub (`index.html`, clase `.tool-tile.c-<color>` en el `<a class="tool-tile">`, tinte rgba al 20% sobre `.tool-icon-tile`), y (2) un `border-top:3px solid <color>` en **todos** los paneles `.win` de esa herramienta. Colores asignados — no los cambies sin que el usuario lo pida: Film Scanner `#4A7DEE` (azul, clase `c-blue`), Photo Editor `#7FCB68` (verde, `c-green`), LUT Lab `#B073FF` (violeta, `c-violet`), Image Converter `#FF8A5B` (naranja, `c-orange`), Favicon Generator `#FF6FA5` (rosa, `c-pink`), QR Generator `#4DD0C0` (teal, `c-teal`). Las páginas que no son herramientas (`about.html`, `terms.html`) NO llevan color de identidad — se quedan con el borde superior neutro (`var(--border-strong)` o blanco), porque no son "una herramienta". Si agregás una herramienta nueva, elegile un color que no se repita con los 6 de arriba y aplicalo en esos dos lugares.
- **Mascota "Iggy" (dibujo real del usuario, desde septiembre 2026)**: el placeholder fantasmita de trazo blanco **ya no existe** — el usuario mandó su propio dibujo de Iggy (un bull terrier con traje y corbata, fumando, estilo manga — la referencia real de JoJo's Bizarre Adventure) y pidió usarlo como mascota oficial. **Hubo dos versiones del procesamiento; la que quedó es la v2:**
  - v1 (descartada): invertir todo a blanco-sobre-transparente (tinta negra → blanco opaco, papel blanco → transparente). El usuario la vio y pidió explícitamente "al revés" — perdía todos los rellenos negros ricos del dibujo original.
  - **v2 (la actual)**: se mantienen los colores originales del dibujo (tinta negra, blancos/resaltados del papel) tal cual, y se recorta a silueta (todo lo que es "fondo de la hoja" conectado al borde de la imagen vía flood-fill se vuelve transparente; los blancos *encerrados* dentro del dibujo — ojos, brillos de las orejas, etc. — se mantienen opacos porque son parte del dibujo, no del fondo). Después se agrega un **halo/borde blanco de unos pocos px** alrededor de toda la silueta (dilatar la máscara del personaje y rellenar el anillo con blanco), para que el contorno se vea recortado contra el fondo negro del sitio incluso donde el borde del dibujo es tinta negra (que si no, se fundiría con la página). Resultado: mantiene todo el detalle y sombreado original del artista, con un contorno blanco tipo "sticker" que lo separa del fondo. Funciona bien tanto en fondo negro (el sitio) como en fondo blanco (por eso no hace falta ponerle un cuadrado sólido detrás para el favicon/ícono de marca — ver abajo).
  - El pipeline (Pillow + scipy.ndimage para el flood-fill/dilatación) no quedó guardado como script en el repo — si hay que reprocesar el arte original (por ejemplo si el usuario manda una versión nueva), rehacé estos pasos a mano: (1) máscara de tinta por luminosidad, (2) flood-fill de blancos conectados al borde = fondo, (3) todo lo demás = personaje (RGB original, alfa 255), (4) dilatar la máscara del personaje ~7px y rellenar ese anillo de blanco por debajo, (5) recortar al bounding box.
  - `mascot.png` — el cuerpo completo, usado como `<img class="mascot">` en el hero de `index.html`. Es una imagen rasterizada (no SVG), así que el parpadeo de ojos que tenía el placeholder viejo (animación por sub-elemento SVG) **no es posible** con este formato — solo queda la animación de flotar (`@keyframes mascotFloat`, sigue andando sobre el `<img>`). Si el usuario pide que vuelva a parpadear, hace falta pedirle los ojos como capa/archivo aparte.
  - `brand-icon.png` (128×128, cabeza recortada a cuadrado, mismo tratamiento v2, **fondo transparente** — no lleva cuadrado sólido detrás porque el halo blanco ya le da contraste en cualquier fondo) — el ícono chico de marca en el `.brand` de las 9 páginas.
  - `favicon.ico` (multi-tamaño real: 16/32/48 en un solo archivo, generado con `Image.save(..., sizes=[...])` de Pillow — **ojo**: hay que llamar `.save()` sobre la imagen master de alta resolución, no sobre una ya redimensionada a 16×16, o Pillow solo guarda un tamaño), `favicon-16x16.png`, `favicon-32x32.png`, `android-chrome-192x192.png`, `android-chrome-512x512.png`, y `site.webmanifest` — todos con fondo transparente igual que `brand-icon.png`. `apple-touch-icon.png` (180×180) es la excepción: fondo negro sólido, porque iOS lo muestra en un tile propio y se ve mejor opaco. Las 9 páginas tienen el mismo bloque de 5 `<link>` en el `<head>` (`icon` x3, `apple-touch-icon`, `manifest`) apuntando a rutas absolutas `/favicon.ico` etc. **Esto reemplazó el favicon viejo que era un SVG embebido como `data:` URI** — ese approach nunca le mostraba ícono a Google en los resultados de búsqueda porque Google necesita un archivo real y estable en una URL, no un data URI inline. No vuelvas al patrón `data:image/svg+xml` para el favicon.
  - Si el usuario redibuja la mascota de nuevo, hay que repetir el proceso v2 completo para los 3 assets (`mascot.png`, `brand-icon.png`, el set de favicons) — no volver al tratamiento v1 (blanco-sobre-transparente) salvo que el usuario lo pida explícitamente.
  - `og-image.png` (1200×630, en la raíz) — tarjeta para compartir en redes (Open Graph/Twitter), fondo negro con la mascota completa a la derecha y "Dr Iggy's" + tagline en Consolas Bold a la izquierda. Generada una sola vez con Pillow (fuente del sistema `C:/Windows/Fonts/consolab.ttf`), no hay script guardado. Las 9 páginas comparten esta misma imagen vía `og:image`/`twitter:image` — si se agrega una herramienta nueva, no hace falta una tarjeta custom por herramienta, reusar esta.
- **Nada de gimmicks de terminal tipo `$ whoami` / `$ ls ./tools` como texto decorativo estático** — se probaron en el hub y el usuario los sacó explícitamente por sentirse "edgy" / forzados. El look de terminal se logra con la tipografía, los bordes cuadrados y el borde superior grueso, no con texto de prompt falso. La única excepción es el tagline del hero en `index.html`, que sí tiene una animación real de tipeo (ver más abajo) — eso el usuario lo pidió y le gustó.
- El chrome de ventana falso (barra de título con minimizar/maximizar/cerrar decorativo, estilo Windows) **ya no existe** — se reemplazó por un nav simple (menú hamburguesa + marca + controles a la derecha). No lo reintroduzcas.
- **Menú hamburguesa**: las 9 páginas tienen un botón `#btnMenu` (ícono de 3 líneas) a la izquierda de la marca, que abre un `.nav-menu` desplegable con links a Home + las 6 herramientas + About + Terms, con la página actual resaltada (`class="current"`, fondo blanco/texto negro). Pedido explícito del usuario ("arriba a la izquierda... un menu desplegable"). El patrón (`.hamburger`, `.nav-menu`, `.menu-backdrop`, más el JS `toggleMenu()`/cierre con click-afuera/Escape) es idéntico en las 9 páginas — copialo tal cual si agregás una herramienta nueva. **Ojo**: un `<button>` no hereda `color` del body por defecto en algunos navegadores — si agregás un botón con ícono SVG `stroke="currentColor"`, ponele `color` explícito en su CSS o el ícono queda invisible (pasó una vez con `.hamburger` en `index.html`).
- **Feedback al hacer click**: casi todos los `button` ya tienen `:active{ transform:scale(.97) }` (o similar) para dar feedback táctil — es un pedido explícito del usuario ("mas feedback cuando apretas las cosas"). Los `.tool-tile` del hub también tienen `:active{ transform:scale(.97) }` + cambio de borde. Si agregás un elemento clickeable nuevo, dale el mismo tipo de feedback.
- El layout de cada herramienta (toolbar arriba, panel de ajustes a la derecha, filmstrip abajo, etc.) sí se mantiene — lo que cambió es solo la piel visual, no la estructura.

**Animación de tipeo en el hero (`index.html`)**: el párrafo bajo el título ("Small, free, no-signup tools...") se tipea letra por letra con un cursor parpadeante, y a mitad de camino simula un error de tipeo (escribe una palabra con dos letras invertidas, pausa, borra, y la vuelve a escribir bien) antes de terminar la frase. Función `runTypewriter()` en el `<script>` de `index.html`; se vuelve a correr cada vez que cambia el idioma. Pedido explícito del usuario — no lo saques ni lo simplifiques a un tipeo sin errores.

## Convenciones de código específicas de este proyecto

1. **i18n casero**: cada página tiene un objeto `I18N = { en:{...}, es:{...} }` y una función `t(key, vars)`. El idioma se guarda en `localStorage` bajo la clave `drIggyLang` y **se comparte entre todas las páginas** — si cambiás el idioma en una herramienta, tiene que reflejarse en las demás. Los botones de idioma son dos (`EN`/`ES`), no un toggle único.

2. **Botón de pantalla completa**: cada página tiene un solo ícono (`#btnFullscreen`) en el nav que hace toggle real de fullscreen (entra si no está, sale si ya está). Ya no hay minimizar/maximizar/cerrar por separado — eso era del chrome de ventana viejo (ver "Identidad visual").

3. **El `Dockerfile` usa `COPY . .`, no `COPY *.html .` ni listas de archivos.** Hubo un bug real y doloroso donde se listaban archivos por extensión y un archivo nuevo (`robots.txt`, `sitemap.xml`) no se copiaba al contenedor. No vuelvas a ese patrón.

4. **Despliegue**: la app corre en una VM de Google Cloud (`e2-micro`, capa gratuita), con Docker, detrás de Cloudflare (dominio `driggys.com`, modo SSL "Flexible"). El repo de GitHub tiene un Action (`.github/workflows/deploy.yml`) que hace SSH a la VM y corre `git pull && docker build && docker run` en cada push a `main`. **Ojo con `sudo` en ese script** — cuando se ejecuta sin terminal interactiva (como hace GitHub Actions), `sudo` pide contraseña y falla; el usuario en la VM ya tiene permiso de Docker sin `sudo`, así que el script de deploy no debe usar `sudo` en los comandos de `docker`.

5. **RAW**: el decodificado de archivos RAW (`.cr3`, `.nef`, `.arw`, etc.) pasa por un endpoint `/api/decode-raw` en `server_prod.py`, que usa `rawpy`. El navegador nunca decodifica RAW por su cuenta. Cualquier herramienta nueva que necesite abrir RAW debe pegarle a ese mismo endpoint (ya lo hace `photo-editor.html`, copiado de `film-scanner.html`).

6. **Traspaso de fotos entre herramientas**: hay un mecanismo con `IndexedDB` (base `drIggysHandoff`, store `images`, clave `pending`) para mandar una foto procesada de una herramienta a otra sin pasar por el servidor ni pedir que el usuario descargue/vuelva a subir. Mirá el botón "Edit in Photo Editor" en `film-scanner.html` (que escribe en la DB) y el `checkHandoff()` en `photo-editor.html` (que la lee al cargar) para el patrón exacto si agregás más herramientas.

7. **Nada de librerías de IA/ML (ni de ninguna librería externa, en general) sin verificar antes con un ejemplo real funcionando.** Hubo una saga larga y dolorosa tratando de meter super-resolución con modelos que resultaron no existir en las rutas documentadas, o eran para otro dominio (anime en vez de fotos reales), etc. Antes de integrar cualquier librería nueva: buscá un ejemplo de código real y andando (no solo documentación oficial, que puede estar desactualizada), confirmá el nombre exacto del export/import y la versión, y probalo de verdad en el navegador (Playwright o el Browser tool) antes de darlo por bueno. Librerías ya integradas y con evidencia real de que el patrón funciona: `@imgly/background-removal` (`photo-editor.html`, import ES module desde jsDelivr), `@jsquash/{jpeg,png,webp,avif,jxl}` + `heic-to` + `UTIF.js` (`convert.html`), `qr-code-styling@1.9.2` (`qr-generator.html`, global `QRCodeStyling` vía `https://cdn.jsdelivr.net/npm/qr-code-styling@1.9.2/lib/qr-code-styling.js`, soporta logo incrustado con `image`/`imageOptions` y exporta PNG/SVG reales vía `getRawData()`).

## Cómo se prueban los cambios en este proyecto

El entorno tiene Playwright con Chromium instalado. El patrón usado durante todo el proyecto:
```python
from playwright.sync_api import sync_playwright
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page(viewport={'width':1300,'height':900})
    errs = []
    page.on('pageerror', lambda e: errs.append(str(e)))
    page.goto('file:///ruta/al/archivo.html')
    # ...interactuar, hacer click, subir archivos con page.set_input_files()...
    page.screenshot(path='check.png', full_page=True)
    print(errs)
```
Usalo para cualquier cambio de UI o de lógica antes de decir que algo "ya funciona". El usuario no puede leer código para verificar — necesita ver capturas o texto de confirmación real.

**Nota**: `file://` bloquea algunos recursos (CDNs externos como jsDelivr a veces devuelven 403 bajo ese protocolo, IndexedDB puede comportarse distinto entre pestañas del mismo `file://`). Para probar RAW real hace falta el servidor Python corriendo (`python server_prod.py` o el `server.py` local), y para IA real hace falta estar en un origen `http(s)://` de verdad, no `file://`. Avisale esto al usuario si hace falta probar en la VM real en vez de local.
